## 0. Главное за 60 секунд

PARSER — локальное приложение для одного продавца сайтов (веб-студии). Оно:

1. собирает организации из карт (Google, Яндекс, 2ГИС) по сетке квадратов;
2. склеивает дубликаты и сети в одну карточку;
3. показывает карточку, которая помогает продать сайт: потенциал, зацепки, оффер, готовое первое сообщение, аудит сайта, быстрые контакты;
4. по кнопке «Обогатить» вытаскивает контакты из сохранённых ответов источников и обходит сайт бизнеса;
5. опционально генерирует сообщение через OpenAI-совместимую LLM. **Без ключа всё работает на шаблоне.**

Ключевые принципы:

- **Не выдумывать данные.** Только то, что реально пришло из источника, со страницы сайта или лежит в БД. Демо помечается.
- **Локальный запуск.** `run.bat` → `http://127.0.0.1:8777`. Публичный хостинг не нужен.
- **Без ИИ приложение полноценно.** ИИ — улучшение, а не зависимость.
- **Реальные лиды и секреты не коммитятся.** `data/parser.db*`, `.env`, `.venv`, `__pycache__` — вне git.

Текущее состояние: **106 тестов OK**, в рабочей базе **69 карточек и 166 привязок к источникам**, `integrity_check ok`.

## 1. Цель и рамки

**Пользователь:** один человек, который продаёт создание сайтов малому бизнесу. Работает вручную: находит бизнес, открывает карточку, копирует сообщение, пишет в мессенджер или звонит.

**Сценарий:**

```
выбрать нишу и город → скан → список лидов → карточка
→ «Обогатить» → прочитать потенциал и зацепки
→ скопировать сообщение (или сгенерировать ИИ)
→ отметить статус / избранное / заметку
```

**Что сознательно не делается:**

- нет авторизации, ролей, мультитенантности;
- нет публичного облака и биллинга (GitHub Codespaces — только опциональный способ запуска);
- нет массовых рассылок и автоматической отправки сообщений;
- нет парсинга персональных данных «в глубину»: только публичные карточки организаций;
- нет обещаний и цифр, которых нет в данных.

## 5. Данные

### 5.1 Таблицы

**`business`** — одна карточка организации (сеть = одна карточка).

Ключевые поля:

- `id` — стабильный внутренний id;
- `source`, `source_id` — первый источник;
- `name`, `category`, `address`, `lat`, `lon`;
- ключи дедупликации: `name_key`, `compact_key`, `brand_key`, `address_key`, `phone_keys`, `site_key`;
- контакты: `phone`, `phone_norm`, `website`;
- `rating`, `reviews_count`, `price_range`, `hours`;
- `photos_json`, `site_json` (аудит сайта), `url`;
- `status`, `is_favorite`, `note`, `is_demo`;
- `first_seen`, `updated_at`.

**`business_source`** — привязка карточки к источнику: `business_id`, `source`, `source_id`, `url`, `payload_json`. Именно здесь лежат сырые ответы 2ГИС/Яндекса, из которых «Обогатить» достаёт данные.

**`business_location`** — точки сети: адрес, телефон, координаты, `address_key`, источник, URL.

**`fact`** — отдельный факт со страницы или источника: `kind` (`email`, `phone`, `price`, `photo`, `social`, `director`, `description`, `inn`, `hours`, `address`), `value`, `source_url`, `fetched_at`. Без `source_url` факт не создаётся.

**`scan_job`** — задание скана: bbox, город, запросы, прогресс, статус.

**`scan_cell`** — ячейка сетки: `ix`, `iy`, статус, число найденных.

### 5.2 Миграции

Схема создаётся через `CREATE TABLE IF NOT EXISTS`, новые колонки добавляются через `ALTER TABLE` с проверкой существующих. Так появился `site_json`, `city` и `queries_json` у `scan_job`, `address_key` у `business_location`. Отдельного фреймворка миграций нет — это осознанно: проект локальный, одна SQLite-база.

### 5.3 Достоверность

Три уровня (подробно в `docs/DATA_INTEGRITY.md`):

1. **Факт источника** — ответ карт, лежит в `business_source.payload_json`.
2. **Факт со страницы** — HTML сайта, лежит в `fact` с точным `source_url`.
3. **Демо** — `is_demo=1`, имя начинается с «ДЕМО — ».

Пустое значение остаётся пустым. UI пишет «нет данных», а не придумывает.

## 6. Пайплайн

### 6.1 Сканирование

- `bbox = (min_lon, min_lat, max_lon, max_lat)` в WGS84.
- `cell_deg` по умолчанию `0.05`; число ячеек ограничено 2000, при превышении шаг укрупняется.
- По каждой ячейке вызывается `adapter.search(query, cell_bbox, limit)`, одновременно не более 3 ячеек.
- Категории превращаются в запросы; для каждой категории сетка проходится заново. Максимум 300 запросов за запуск; больше 24 категорий UI помечает как долгий скан.
- Google ищет от центра ячейки с радиусом по диагонали, затем адаптер отбрасывает точки за пределами квадрата (запас 10%).
- Яндекс получает bbox ячейки напрямую.
- 2ГИС не умеет bbox: обходит город целиком и фильтруется по bbox задания; город берётся из `city` или `TWOGIS_CITY`, транслитерируется в slug.
- 2ГИС умеет работать через официальный API (`TWOGIS_API_KEY`) или браузерный парсер.
- Google работает через внешний `gmsc.exe` (gosom/google-maps-scraper), Яндекс — через папку `yamaps_parser`. Эти внешние парсеры не входят в репозиторий; без них работает демо.
- SSE-события: `job` (статус), `cell` (прогресс ячейки), `lead` (новая карточка), `error`.

### 6.2 Дедупликация и сети

Порядок в `db.upsert_place`:

1. Та же запись источника (`source` + `source_id`).
2. **Сеть** — совпадение `brand_key`: название без пробелов, оргформ и родовых слов («Кофейня», «Кафе», «Coffee» и т.п.). Одна сеть — одна карточка, даже если точки в разных районах.
3. **Та же точка** — телефон, адрес (улица + дом), сайт, название и расстояние. Сильный телефон (кроме 8-800), совпадение адреса или название + близость дают склейку. Разные дома — стоп-сигнал.
4. Демо никогда не склеивается с реальными.

При склейке пустые поля дозаполняются, существующие не перезаписываются. Привязка добавляется в `business_source`, адрес и телефон точки — в `business_location`.

Особые правила:

- родовые названия не считаются брендом: две «Кофейни» на разных улицах — две карточки;
- 8-800 — общий номер сети, по нему точки не склеиваются;
- номера из 18 цифр (склейка 8-800 с добавочным в 2ГИС) отбрасываются;
- пустые технические точки не увеличивают `locations_count` и не показываются в списке;
- адрес Яндекса дозаполняет существующую пустую точку, а не создаёт дубль.

CLI для уже накопленной базы (с резервной копией рядом):

```bat
python -m backend.merge_duplicates           :: только отчёт
python -m backend.merge_duplicates --apply   :: склеить
```

### 6.3 Обогащение

`POST /api/leads/{id}/enrich` работает в два этапа:

1. **Payload'ы источников, без сети.** `source_facts.py` разбирает `business_source.payload_json`:
   - 2ГИС: «Веб-сайт 1..3», «ВКонтакте», «Telegram», «WhatsApp», «Телефон 1/2», «E-mail», часы, описание, рейтинг;
   - Яндекс: `site`, `social`, `phone`, `address`, `lat/lon`, `rating`, `reviews`.
   Пустые поля карточки дозаполняются, факты пишутся с URL источника.
2. **Сайт, если он есть.** `enrichment.py` обходит до 6 страниц (главная + `/contacts`, `/about`, `/price`, `/menu`, `/uslugi` и т.п.), таймаут страницы 10 с, общий бюджет 60 с, максимум 3 МБ HTML, до 12 фото. Из HTML достаются контакты, соцсети, email, телефоны, адрес, часы, цены, фото. Одновременно `site_audit.py` считает технические признаки, результат сохраняется в `business.site_json`.

Статусы ответа:

- `ok` — сайт обойдён;
- `no_site` — сайта нет, но контакты из источников собраны (это **не ошибка**);
- `social_only` — вместо сайта соцсеть, обходить нечего (тоже не ошибка);
- `error` — организация не найдена или фатальная ошибка.

`no_site` и `social_only` — важные сценарии: именно такие бизнесы чаще всего и нужно продавать.

### 6.4 Карточка: потенциал, зацепки, оффер

`intel.py` — чистая функция `build_intel(lead)`. Она не ходит в сеть, не пишет в БД и не меняет карточку. Вызывается на чтении в `db.get_lead`, поэтому всегда соответствует текущим данным.

Выход:

```json
{
  "score": 80,
  "label": "высокий",
  "summary": "…",
  "hooks": [{"code": "no_site", "title": "…", "detail": "…", "kind": "gap", "weight": 30}],
  "strengths": [{"code": "high_rating", "title": "…", "detail": "…", "weight": 8}],
  "gaps": [{"code": "no_site", "title": "…", "detail": "…", "weight": 30}],
  "offer": {"title": "…", "why": "…", "bullets": ["…"]},
  "pitch": "Здравствуйте! … Прислать?",
  "contacts": [{"type": "phone", "label": "…", "href": "tel:…"}],
  "site": {"has_site": false, "url": "", "social_only": false, "checks": [], "score": 0}
}
```

**Оценка (`score`)** — от 5 до 98, старт 30:

- нет сайта: +38; вместо сайта соцсеть: +30;
- 2+ точки: +8; 5+ точек: +11;
- рейтинг ≥ 4,5 и ≥ 50 отзывов: +8; ≥ 20 отзывов: +4;
- рейтинг < 4,0: −6;
- нет часов: +3; нет фото: +2; есть телефон: +2;
- у существующего сайта вычитаются баллы за HTTPS, мобильную версию, title, description, форму/запись, меню, доступность. Очень хороший сайт ограничивается 35.

Метки: `≥ 65` — «высокий», `≥ 40` — «средний», иначе «низкий».

**Пустая карточка не должна выглядеть перспективной.** Если нет названия, категории, адреса, телефона, сайта, фактов и точек, `get_lead` принудительно ставит score 5, label «низкий», пустые зацепки и summary «Недостаточно данных…». Иначе «нет сайта» давало бы высокий потенциал пустой записи.

**Зацепки (`gaps`)** — это поводы для разговора, а не диагнозы:

- `no_site`, `social_only`;
- `site_http`, `site_no_mobile`, `site_no_description`, `site_no_booking`, `site_no_menu`, `site_unreachable`;
- `few_reviews`, `low_rating`, `no_hours`, `no_photos`.

Сильные стороны: `high_rating`, `has_phone` и т.п.

**Оффер** выбирается по категории и названию:

| Группа | Оффер |
|---|---|
| `food` | Сайт с меню, адресами и онлайн-заказом |
| `beauty` | Лендинг с онлайн-записью |
| `auto` | Сайт-визитка с заявкой и прайсом |
| `retail` | Каталог с доставкой и самовывозом |
| `default` | Лендинг с контактами и формой заявки |

Категория определяется по ключевым словам. Важная деталь: короткие слова «бар», «спа», «еда», «авто» проверяются по границе слова, а не подстрокой. Иначе «кофейные автоматы» попадали в авто-услуги из-за «авто» внутри «автоматы». Для авто-тематики добавлены явные составные ключи: «автосервис», «автомойк», «автосалон», «автошкол», «автозапчаст», «автотехцентр», «автоэлектрик».

### 6.5 Сообщение для первого контакта

Шаблон (`build_intel()["pitch"]`) собран по схеме холодного B2B-сообщения:

1. **Наблюдение** — название, сфера, число точек, рейтинг. Доказывает, что карточку действительно открыли.
2. **Последствие для клиента** — «сайта нет: меню, цены и адреса разбросаны по картам и соцсетям; заказать можно только по телефону или в переписке». Наблюдение, а не обвинение.
3. **Один оффер** — что получит бизнес, без списка функций.
4. **Одна выгода** — «клиенту проще выбрать и заказать, а вам — меньше пустых звонков».
5. **Лёгкий CTA** — «Могу прислать макет главной — посмотрите, подходит ли. Прислать?»

Правила:

- 300–750 символов, 4–6 коротких предложений;
- без «Предлагаю вариант», «Внутри —», «Когда можно созвониться?», «Пишу по карточке», «10–15 минут»;
- без markdown, эмодзи, заглушек `[имя]`, гарантий и выдуманных кейсов;
- заканчивается вопросом, на который легко ответить «да» или «нет»;
- для сайта с проблемами — конкретика («открыл coffee-like.com с телефона: нет HTTPS») и предложение короткого разбора, а не сразу «сделаем новый сайт»;
- для соцсети — «Вместо сайта — только Telegram…»;
- для пустой карточки — осторожная формулировка без названия.

Пример для Essence Coffee:

> Здравствуйте! Увидел «Essence Coffee» в справочнике — кофейные автоматы, 3 точки, рейтинг 5,0 (1 отзыв). Сайта нет: меню, цены и адреса точек разбросаны по картам и соцсетям. Заказать можно только по телефону или в переписке. Я делаю сайты для кофеен и небольших сетей. Начать можно с одной страницы: меню с ценами, адреса точек и кнопка WhatsApp. Клиенту проще выбрать и заказать, а вам — меньше пустых звонков. Могу прислать макет главной — посмотрите, подходит ли. Прислать?

### 6.6 ИИ (опционально)

`ai.py` работает с любым OpenAI-совместимым API: OpenAI, OpenRouter, Ollama, vLLM.

Переменные окружения:

| Переменная | По умолчанию | Смысл |
|---|---|---|
| `LLM_API_KEY` | — | основной ключ |
| `OPENAI_API_KEY` | — | запасной ключ, если `LLM_API_KEY` не задан |
| `LLM_BASE_URL` | `https://api.openai.com/v1` | базовый URL |
| `LLM_MODEL` | `gpt-4o-mini` | модель |
| `LLM_TIMEOUT` | `25` | таймаут, 5–60 с |

Поведение:

- без ключа `generate_pitch` сразу возвращает `not_configured` и **не ходит в сеть**;
- модель получает system-промпт и компактный JSON только с нужными полями: название, категория, адрес, сайт, телефон, рейтинг, отзывы, часы, число точек, источники, `site_audit`, `intel` (label, offer, summary, зацепки);
- промпт требует структуру «наблюдение → последствие → один оффер → один простой шаг», 350–650 символов, без канцелярита и выдумок;
- ответ чистится от markdown/кавычек, затем валидируется: длина 250–900 символов, отсутствие banned-фраз («предлагаю вариант», «внутри —», «когда можно созвониться», «спектр услуг», «гарантируем» и т.п.);
- при любой ошибке API, таймауте, пустом ответе, плохой длине или шаблонной фразе возвращается `ok: false` с причиной, а фронтенд показывает шаблон из карточки;
- ключ никогда не попадает в ответы и логи.

`POST /api/leads/{id}/pitch` возвращает `source: "ai" | "template"`.

## 8. Frontend

Тёмная тема, три колонки: фильтры/скан, список лидов, карточка. Без сборки.

Карточка показывает:

- название, категорию, адрес, рейтинг, число отзывов, часы, источник;
- бейдж «сеть · N» и список точек;
- блок **«Потенциал»**: score, метка, summary, зацепки и сильные стороны;
- блок **оффера**: что предложить и почему;
- **сообщение** с кнопкой «Копировать» и кнопкой ИИ-генерации;
- **аудит сайта**: HTTPS, мобильная версия, title, description, форма, меню, цены, CMS;
- быстрые контакты: телефон, WhatsApp, Telegram, VK, email, сайт;
- источники, факты, заметку и статус.

Важные детали реализации:

- `#detail-content` одновременно является скролл-контейнером и контентом. Класс `detail-content` задаёт `padding: 20px 22px 26px`; раньше у элемента был только `detail-scroll`, поэтому отступа от левой стенки не было. Исправлено добавлением класса.
- При обновлении карточки сохраняется позиция прокрутки; при открытии другой карточки — сбрасывается.
- Версия статики в `index.html` (`?v=20261118b`) нужна, чтобы браузер не держал старый CSS/JS.
- Кнопка «Обогатить» показывает статус и не считает `no_site`/`social_only` ошибкой.

## 10. Принятые решения и причины

1. **`intel` считается на чтении, а не хранится.**
   Карточка всегда соответствует текущим данным, не нужна миграция при изменении формулы, нет риска устаревших оценок. Сеть не используется, поэтому это дёшево.

2. **Аудит сайта хранится в `business.site_json`, а не в отдельной таблице.**
   Аудит — это снимок одного сайта, а не история. Отдельная таблица усложнила бы схему без пользы.

3. **`enrich` сначала читает payload'ы, потом идёт на сайт.**
   Данные источников уже оплачены и лежат локально; сеть — дорогая и ненадёжная часть. Даже без сайта обогащение даёт результат.

4. **`no_site` и `social_only` — не ошибки.**
   Это самые ценные лиды для продажи сайтов. Ошибка в UI оттолкнула бы от них.

5. **Пустая карточка принудительно получает низкий потенциал.**
   Иначе отсутствие сайта давало бы высокий score записи, с которой нечем работать.

6. **Оценка и оффер — эвристики, а не ML.**
   Нужна предсказуемость и объяснимость: продавец должен видеть, почему карточка «горячая». ML без данных был бы имитацией.

7. **ИИ опционален и валидируется.**
   Приложение не должно ломаться без ключа. Модель склонна к шаблонам и выдумкам, поэтому ответ проверяется по длине и banned-фразам, а при провале заменяется шаблоном.

8. **Промпт требует один CTA и запрещает созвон в первом сообщении.**
   Просьба о звонке повышает барьер. «Прислать макет?» — маленький шаг, на который легко ответить.

9. **Категория проверяется по границе слова для коротких ключей.**
   Подстрока «авто» ломала «кофейные автоматы». Явные составные ключи сохраняют авто-тематику.

10. **Дедупликация по `brand_key` важнее координат.**
    Одна сеть может быть в разных районах; координаты — самый слабый сигнал. При этом разные дома — стоп-сигнал, чтобы не склеить соседние точки.

11. **Пустые технические точки игнорируются.**
    Источники иногда отдают точку без адреса и телефона. Она не должна раздувать `locations_count` и ломать список точек.

12. **SQLite, а не Postgres.**
    Локальный проект на одного пользователя. WAL достаточно; проще резервное копирование и перенос.

13. **Ванильный фронтенд, а не React.**
    Нет сборки, зависимостей и сюрпризов при запуске у друга. Одна страница и один JS-файл.

14. **Реальные данные не коммитятся.**
    `data/parser.db*` — это лиды и персональные контакты. В git только код и `.env.example`.

15. **Демо отделено от реальных данных.**
    `is_demo=1` и префикс «ДЕМО — » не дают тестовым записям смешаться с настоящими и склеиться с ними.

## 12. Подводные камни

1. **Windows + кириллица.** PowerShell может показывать `?`. Для Python-проверок задавать `PYTHONUTF8=1` и `PYTHONIOENCODING=utf-8`. Не считать это порчей данных.

2. **SQLite WAL.** Рядом с `parser.db` могут быть `-wal` и `-shm`. Для архива/копии делать снапшот через `sqlite3.Connection.backup`, а не копировать файл на живой базе. В git их не добавлять.

3. **2ГИС не отдаёт улицу в payload.** В `payload_json` есть «Город / Район / Микрорайон», но не улица и дом. Не собирать адрес из этих полей — получится мусор. Адрес берётся из карточки или Яндекса.

4. **`site=none` не работает.** Только `site=no` и `site=yes`.

5. **`#detail-content` — и скролл, и контент.** Если снова поменять разметку, легко потерять padding. Класс `detail-content` должен оставаться на элементе.

6. **Подстрока «авто».** Не возвращать проверку без границы слова, иначе «автоматы», «автоматизация» и подобные снова станут авто-услугами.

7. **Пустая карточка.** Любая новая эвристика не должна снова делать пустую запись «горячей».

8. **ИИ любит шаблоны.** Не ослаблять валидацию без причины. Проверять длину и banned-фразы.

9. **Кэш фронтенда.** После правок CSS/JS менять `?v=` в `index.html`, иначе браузер покажет старое.

10. **Внешние парсеры.** `gmsc.exe`, `yamaps_parser`, браузерный 2ГИС не входят в репозиторий. Без них доступен только демо-режим; это нормально.

11. **Права и ToS.** Автоматический сбор Google/Яндекс/2ГИС может нарушать их соглашения. Проект локальный и учебно-рабочий; не превращать его в публичный сервис без юридической проверки. Подробнее — `docs/RESEARCH.md` и `docs/DATA_INTEGRITY.md`.

12. **Персональные данные.** В базе телефоны и адреса организаций. Не публиковать базу, не отправлять архив посторонним, не коммитить.

## 14. Правила для следующей модели

1. **Сначала прочитай** `README.md`, `CONTRACT.md`, `docs/DATA_INTEGRITY.md`, этот файл. Не меняй контракт модулей без причины.
2. **Не выдумывай данные** и не добавляй в UI цифры, которых нет в БД. Если данных нет — «нет данных».
3. **Не коммить** `data/parser.db*`, `.env`, `.venv`, `__pycache__`, реальные лиды.
4. **Не делай ИИ обязательным.** Любая фича должна работать без ключа.
5. **Сохраняй стиль:** русские комментарии и docstring, простые функции, без тяжёлых зависимостей.
6. **Проверяй полным прогоном** `python -m unittest discover tests` перед коммитом.
7. **Для UI-правок** поднимай сервер и проверяй в браузере: отступы, прокрутку, копирование, ошибки в консоли.
8. **Для изменений `intel`/`ai`** добавляй тест на форму и на запрещённые фразы.
9. **Не превращай проект в SaaS** без отдельного запроса: локальность — осознанное решение.
10. **Если сомневаешься между «красиво» и «честно»** — выбирай честно. Достоверность данных важнее эффектной карточки.
